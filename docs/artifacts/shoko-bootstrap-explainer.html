01 / Architecture

Keep business meaning.
Change the binding.

The application owns its vocabulary: “registration completed”, “account exists”, “user exists”. Shōko owns how descriptions are inspected, executed, and judged. A binding supplies the actual sources and operations for one environment and implementation.

shoko-core

The verification contract

Inspectable scenarios, typed references, deadlines, correlation, capability checks, evidence coverage, and versioned results. Database-independent; explicit v1 JSON results.

shoko-adapters

The evidence connections

Implemented PostgreSQL, HTTP, Kiroku, and Message DB helpers for context-owned bindings. Concrete sources implement core contracts rather than defining new verdict semantics.

shoko-cli

The operator interface

List, explain, check, and run compiled scenarios. A reusable host library lets each context supply its own scenario registry and vocabulary.

03 / Evidence & verdicts

A result is only as strong
as its evidence.

Descriptions remain inspectable before effects run. Execution then records what was observed, where it came from, which run it belongs to, and what interval the source can actually cover.

Describe the consequence, not the query.

Scenario

A typed description of fixtures, actions, and expectations. Construction does no IO.

Observation

A binding reads a domain fact and attaches its source, identity, timing, and coverage.

Expectation

The core judges the observation using one of three bounded operators.

Evidence

Positive witnesses and negative search records remain in the result, including gaps and failures.

CURRENT PUBLIC APICompiled consumer excerpt
accountScenario =
  scenario "toy-account" "Provision a toy account" "v2" $ do
    qualified <- given "agent" $
      accept ["ready"] Qualified
    created <- act "create" $
      accept ["created"] (Create (fromRef qualified) True)
    expect $
      eventually "account-exists" $
        observe "is-created" (Created (fromRef created)) id

From the compiled account consumer, which supplies the operation vocabulary and two storage bindings. This local example verifies the library; registration staging acceptance is separate.

POSITIVE SCENARIO → PASS

The operation succeeds.

Valid input completes the documented workflow and creates the expected downstream facts.

NEGATIVE SCENARIO → PASS

The right rejection occurs.

A declared invalid-input case returns the specific rejection and preserves the required domain invariants. Unexpected success or a different rejection is Fail.

MISSING EVIDENCE → UNKNOWN

An outage is inconclusive.

A timeout or inaccessible source cannot count as successful rejection. Negative assertions still need adequate evidence coverage.

Expectation

Scroll the timeline horizontally to see the full window →

Illustrative 6-second window. Current defaults: 30s total, 10s for eventually, 100ms polling, plus 5s cleanup grace; staging chooses explicit budgets. A closing history read may use remaining run time after the evidence cutoff. Cleanup time cannot collect more evidence.

Pass

A matching witness was obtained by the deadline. It can satisfy eventually even if it occurred before the first poll.

CLI exit 0 · conclusive witness
Pass / exit 0Evidence satisfies the declared expectation and its required coverage.
Fail / exit 1A conclusive witness or completed search establishes an expectation failure.
Unknown / exit 3Missing access or incomplete coverage prevents a conclusive verdict.
Absence needs a search record. “No rows returned” and “the database could not be reached” are different observations. A finite never requires complete coverage of its interval; polling a mutable table cannot establish what happened between samples. Invalid invocation or policy uses exit 2; unexpected runner faults use exit 4.

05 / Configuration & foundation

Use Settei.
Make settings explainable.

The host declares typed configuration once. Settei resolves YAML, explicit environment bindings, and named CLI options, retaining safe source provenance. Shōko’s core receives typed values and enforces scenario policy.

01 / LOWESTDeclared defaults
02Explicit YAML file
03Bound env variables
04 / HIGHESTNamed CLI options

Precedence applies only to supported operational settings. An invalid winning value is an error; it does not fall back to a lower layer.

Staging is the target. CI is a caller. Connect from an operator shell or automation with the approved access. Record the actual cluster, namespace, deployment, and data endpoints; a namespace label alone does not isolate external dependencies. Setup and cleanup manage only owned test data and verifier access resources.

Strict, attributable input. Reject unknown keys. Preserve safe winning and shadowed origins. Keep absent and empty environment values distinct.

Secrets stay out of reports. Show credential reference names during inspection without reading their values; resolve values only for a live run. Use Settei’s secret-safe diagnostics.

Policy has a clear owner. Environment and CLI overrides cannot enlarge capability grants. --allow-synthetic is separate per-run consent.

One integration boundary. settei, settei-yaml, settei-env, and settei-optparse-applicative live in the CLI/host layer.

Build on the shared foundation

Consistent tools.
Small package boundaries.

The Seihou nix-haskell-flake environment provides GHC 9.12.4. The packages follow Jitsurei’s Haskell practices: GHC2024, strict records, explicit deriving, and a small project prelude. Keep generated Nix files managed; place project wiring in flake.module.nix.

06 / Proposed next API

Reuse workflow blocks.
Keep their meaning visible.

Plan 08 proposes composition before the real context-owned host is written. It is a standalone plan with five unimplemented milestones, outside MasterPlan 01’s seven work streams.

Current implementation

One fixed scenario and explicit binding

Typed references connect named steps. A single vocabulary and hand-written binding describe the run; one correlation plan is selected for it. All expectations activate after the action sequence.

Individual expectations can be reused. Namespaced workflow fragments, combined vocabularies, per-operation handler assembly, and per-observation correlation selection are not yet public features.
